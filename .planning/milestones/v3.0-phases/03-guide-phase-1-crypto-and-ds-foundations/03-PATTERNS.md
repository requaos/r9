**Claim-or-fail cell, the model for the chained overflow's `WRITING` (0xFF) claim** (lines 170-197, 216-226):
```rust
pub struct BusyCell<T> {
    busy: AtomicBool,
    data: UnsafeCell<T>,
}
...
    pub fn enter(&self) -> Option<BusyGuard<'_, T>> {
        if self.busy.swap(true, Ordering::AcqRel) {
            return None;
        }
        Some(BusyGuard { cell: self })
    }
...
    fn deref_mut(&mut self) -> &mut T {
        // SAFETY: Deref's invariant — the guard is the cell's single owner.
        unsafe { &mut *self.cell.data.get() }
    }
...
    fn drop(&mut self) {
        self.cell.busy.store(false, Ordering::Release);
    }
```
This is the sound shape RESEARCH Pitfall 6 asks for: the slot is an `UnsafeCell`, the write happens only after an atomic claim succeeds, and the SAFETY argument is tied to that claim. Do not write through a pointer cast from `&T` (compendium listing 9.4).

/// Simple bitmap.  Bear in mind that logically, bit 0 is the rightmost bit,
/// so writing out as bytes will have the bits logically reversed.
struct Bitmap<const SIZE_BYTES: usize> {

}

impl<const SIZE_BYTES: usize> Bitmap<SIZE_BYTES> {
    pub const fn new(init_value: u8) -> Self {
        Self { bytes: [init_value; SIZE_BYTES] }
    }

    /// Is bit `i` within the bitmap set?
    pub fn is_set(&self, i: usize) -> bool {
        let byte_idx = i / 8;
        let bit_idx = i % 8;
        let byte = self.bytes[byte_idx];

    }
