<objective>
Deliver boot configuration to the arm64 ROOT env seed through the DTB, starting with a measurement of whether the DTB carrier works at all.

Purpose: ARM-10 (inventory item c1). x86_64 delivers `init=/amd64/init -c` through the multiboot2 command line; arm64 has no reader and no launcher seam.
Output: one Harvey commit (launcher seam; a second one for the property default on the `r9-property` carrier), two r9 commits (reader, parser, merge; capability extents), the delivery measurement on record, one owner decision on the carrier.

Scope note (revision): Task 4, the virtio capability-extent hardening, was moved here from 20-15. Nothing was dropped or thinned: the task text, its verify and its acceptance are unchanged apart from the plan number. Stated assumption for it (A-extents): the live qemu device's notify capability ends exactly at the BAR boundary (x86_64's own comment); the ported check must not reject it, and Task 4's gate runs prove it on HVF and TCG.

Stated assumption under test (A-carrier): a `bootargs` string property that `fdtput` writes into `/chosen` of the DTB copy survives qemu's load and is what the kernel reads at `DTB_VA`. This is not known. The committed `aarch64/lib/virt-gicv3.dts` header says qemu injects or overrides `/memory` and `/chosen` (rng-seed, kaslr-seed, stdout-path) when loading the blob; the `linux,initrd-start/end` properties the launcher writes do survive (the gates boot), but `bootargs` is a property qemu itself manages for `-append`.
- If it arrives intact and no string appears when none was written: the carrier is `/chosen/bootargs` and Task 3 proceeds as written.
- If qemu drops, rewrites or injects it: the carrier becomes an r9-owned property name on `/chosen` (`r9,bootconf`), which qemu has no reason to touch; Task 3's reader takes the property name the checkpoint selects and nothing else changes.
- If neither property survives: the DTB is not a usable carrier and the plan stops for a re-plan.

Specless-probe note: step 7.95 was skipped visibly (no SPEC at planning time).
</objective>

Parser behaviors to preserve (their host pins are written in 20-17 Task 1 by the measured route; here they are checked by reading the copied code against mb2.rs lines 896-960):
- The empty string and an absent property parse to zero pairs
- `init=/arm64/init -c` is one pair: key `init`, value `/arm64/init -c` (a token without `=` extends the previous value)
- `a=1 b=2` is two pairs in order; a value may contain `=` after the first one
- A leading token without `=`, or an empty key, is `InvalidBootconfToken`
- More than 32 pairs is `TooManyBootconfPairs`; more than 256 bytes before the NUL is `CmdlineTooLong`
- Bytes after the first NUL are ignored
